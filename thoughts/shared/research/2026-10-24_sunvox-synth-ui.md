# SunVox synth UI: facts

## 1. Sources
- `third-party/sunvox_sources-master/{sunvox_engine,sundog_engine,sunvox_api_examples}`: the OPEN-source engine, not just the sv_* API. psynth module sources only (`sunvox_engine/psynth/`): Generator (psynths_generator.cpp 796 lines), FM (553), Kicker (413), Sampler (1512), SpectraVoice (1056), Filter (573), Echo (170), Delay (191), Distortion (166), Flanger (250), Reverb (484), LFO (158), Loop (224), Vocal filter (487); core psynth_net.cpp / psynth.h.
- NOT in the sources: Analog generator, DrumSynth, Compressor, EQ, Filter Pro, WaveShaper, ADSR, Modulator, Amplifier, MultiCtl, Sound2Ctl, Ctl2Note, Velocity2Ctl, Glide, Pitch*, Vibrato, Feedback, GPIO, MetaModule, Vorbis player, MultiSynth, Input (grep of the whole tree finds no such names). Those exist only in the closed official lib.
- Our table of all 41 types: `src/engine/sunvox-modular/SunVoxModuleTypes.ts:15-72`.

## 2. WASM API (two different binaries)
- Source-built wrapper `sunvox-wasm/src/SunVoxWrapper.cpp` (764 lines, CMake `sunvox-wasm/CMakeLists.txt:49-82`, emcmake): exports only create/destroy/load_song/save_song/load_synth/save_synth/get_control_count|name|min|max|value/set_control/get_module_name|count/note_on|off/render/play/stop/pattern getters. NO new_module, connect, ctl_type, enum labels.
- BUT the shipped `public/sunvox/SunVox.js|wasm` (dated 20 Mar 2026) is NOT that build: it exports the official `_sv_*` library API (sv_new_module, sv_connect_module, sv_disconnect_module, sv_remove_module, sv_get_module_ctl_name/min/max/value/type/offset/group, sv_set_module_ctl_value, sv_send_event, sv_save_to_memory, sv_load_module_from_memory, sv_get_module_scope2, ...; `grep -o _sv_ public/sunvox/SunVox.js`). There is no sv_save_module export (only save-song; module save is `saveSynth` message).
- `public/sunvox/SunVox.worklet.js` (hand-maintained, 34 KB, modified 23 Oct) handles: create, destroy, loadSong, saveSong, loadSynth, saveSynth, getModules, getControls, noteOn/Off, setControl, setPatternEvent, mute*, play/stop, getModuleScope, getModuleLevels, getModuleGraph (worklet.js:640-686; reads ctl name/min/max/value, caps 32 controls, no ctl_type, no enum labels).
- GAP: worklet has NO `newModule`/`connectModules`/`disconnectModules`/`removeModule` case (grep count 0), yet `SunVoxEngine.ts:619-656` posts those messages and awaits replies -> the modular editor's add/connect would hang. Verified by grep only (not run in browser).
- Build script for wasm: only sunvox-wasm/CMakeLists.txt (emcmake); the shipped sv_* binary has no build script in repo (unverified origin; likely official prebuilt lib).

## 3. Existing UI
- `SunVoxSynth` (type base.ts:268) editor mode `sunvox-synth`: `SynthTypeDispatcher.tsx:3903+` shows patch name, control count, and `SunVoxPatchLoader` (`components/instruments/SunVoxPatchLoader.tsx`) to load a .sunsynth/.sunvox file; `controls/SunVoxControls.tsx` (160 lines, Knob grid via synth.getControls()) exists but is imported by NO other file (grep over src), so the sunvox-synth editor shows no knobs; `SunVoxFramebufferView.tsx` (479) is the sunvox-wasm-ui framebuffer view. Stored as `config.sunvox: SunVoxConfig {patchData ArrayBuffer|null, patchName, isSong, controlValues, noteTargetModuleId}` (`types/instrument/exotic.ts:683`, default `defaults.ts:1001` = empty patch, so no way to start from scratch). Played by `engine/sunvox/SunVoxSynth.ts` (214) via `InstrumentFactory.ts:783-790` (setModule/setSong of patchData).
- `SunVoxModular` (type base.ts:271): editor `synths/modular/SunVoxModularEditor.tsx` (177): ModularToolbar (shelf prefix sv_), Rack/Canvas/Matrix views, ModulePanel with dynamic `ctl_N` Knobs (`widgets/ModulePanel.tsx:107-117,244`), Load .sunsynth and Save .sunvox buttons. Stored as `config.sunvoxModular: ModularPatchConfig` (`types/modular.ts:190`) with default graph out+analog generator+filter (`defaults.ts:1038`). Played by `engine/sunvox-modular/SunVoxModularSynth.ts` (423): addModule/addConnection/updatePatch/getModuleGraph/loadSunsynthModule/save. So add/connect UI exists, but is broken at worklet level (see 2). It saves a whole .sunvox, not a .sunsynth, and does not write back to `config.sunvox.patchData`.
- Not used from the editor: module descriptors have empty `parameters` (`SunVoxModuleDescriptors.ts:44`); controls come from runtime graph query, no names for enum values, no min/max display units.

## 4. Controller metadata
- In the open sources each ctl is declared by `psynth_register_ctl(synth_id, name, label, min, max, def, type, &value, net)` (psynth.h:208-217). `label` is the unit OR, for selector ctls, a slash list of enum names, e.g. generator `"Type", "tri/saw/rect/noise/dirty", 0,4,0,1` (psynths_generator.cpp:191). 109 register calls across 14 files (grep count: delay 8, distortion 5, filter 8, echo 5, generator 9, flanger 9, fm 17, reverb 7, kicker 9, lfo 6, loop 4, spectravoice 13, sampler 5, vocal 7).
- Runtime from shipped sv_* wasm: name, min, max, value, type, offset, group (sv_get_module_ctl_*); NOT label/enum names/default (sv_get_module_ctl_* has no label getter). Enum labels and defaults must therefore be a TS table (extract from source for the 14 open modules; the ~27 closed module types would need to be read from an official .sunsynth presets/docs or a sv_* run, unverified). The source-built wrapper could add `label`/`def` getters if we rebuilt with a new export (psynth_ctl struct, psynth.h:92).

## 5. Gap list (size = estimate)
1. Worklet: add newModule/removeModule/connectModules/disconnectModules handlers (call `_sv_new_module` etc.) + reply messages that SunVoxEngine already awaits; add ctl_type/offset/group to getModuleGraph. ~150 lines in SunVox.worklet.js; no WASM rebuild (exports exist).
2. New-patch creation: `DEFAULT_SUNVOX` patch from scratch: create handle, add Generator/Analog generator, connect to Output (id 0), serialise to `patchData` via saveSynth; wire "New patch" in SunVoxPatchLoader/dispatcher. ~150 lines, 3 files.
3. Controller metadata table `SunVoxControlMeta.ts`: per module type, ctl name -> unit/enum labels/default/display scale, extracted from psynth_register_ctl calls (script + generated file). Open modules ~110 ctls; closed modules unknown. ~400-800 generated lines + extractor script ~100.
4. Per-module controller panels: Knob (with paramKey/useRef pattern per CLAUDE.md), enum selectors via CustomSelect, grouped by sv ctl_group; extend SunVoxControls to take moduleId and render for every module in the graph. ~300-500 lines, 2-3 files (ModulePanel already renders ctl_N knobs, partial reuse).
5. Module graph: reuse ModularCanvas/Rack views with module add/remove/connect for the single-patch SunVoxSynth (currently only SunVoxModular); sync graph -> config.sunvox.patchData via saveSynth on edit; load roundtrip. ~300-500 lines.
6. Persistence & round trip: SunVoxSynth vs SunVoxModular have separate storage; decide one (SunVoxModular + config.sunvox.patchData unification), .sunsynth export (saveSynth message exists; no UI button for single synth). ~150 lines + migration if storage shape changes.
7. Tests: reachability test through the editor entry with sentinel (module created in wasm), plus regression for the missing-handler hang. ~200 lines.
WASM rebuild: not required for 1-2,4-7 if we stay on the shipped sv_* binary. Required only if we want label/default getters from the engine or switch to the source-built wrapper (which lacks new_module/connect and misses ~27 closed module types, so it cannot replace the shipped binary). Build: `cd sunvox-wasm/build && emcmake cmake .. && make` (emscripten), output to public/sunvox/ (would overwrite the shipped SunVox.js/wasm: do not do without a backup).
